## 2. Goals

v0.7.2 must deliver a production-ready access and operations release that:

1. preserves the accepted v0.7.1 production baseline and existing ledgers,
   history, evidence, recovery, privacy, and authorization invariants;
2. makes staff sign-in, account creation, verified approved-email ownership,
   account application, two-stage review, activation, profile, and access
   administration complete and server-authoritative;
3. separates internal staff workspaces, staff self-service, Request Center,
   Lending Hub, and internal Lending operations by explicit effective access;
4. repairs the required operational workflows without broad redesign;
5. proves the exact candidate in isolated pre-production before any production
   write; and
6. presents one exact-SHA production GO package and waits for the required
   owner phrase.

## 4. Preserved invariants

- Authentication and authorization are server owned. The client never selects
  or asserts a role, scope, approval, state transition, or capability.
- Existing opaque account IDs remain the operational foreign keys. Username,
  email, display name, and account code are not history keys.
- Existing valid account codes are not renumbered for aesthetics.
- Email suffix alone is never authorization. Approved identity classes and
  domains must come from owner-approved configuration.
- Public responses do not enumerate accounts, applications, identities, or
  protected roster matches.
- Protected roster/profile values use the existing encryption pattern and are
  never exposed in public DTOs, logs, evidence, or repository files.
- Lending-only or requester access never implies internal workspace access.
- Administrator and Director do not inherit System Owner authority.
- Inventory changes use the canonical ledger. No direct balance overwrite is
  introduced, and unclassified inventory stays fail closed/non-lendable.
- Verification, application, request, lending, approval, handoff, return, and
  other retryable writes use accepted idempotency and concurrency patterns.
- Audit, ledger, history, release, request, lending, account, identity, and
  evidence records are not hard deleted or rewritten.
- Google, R2, email, and other provider failures never falsely report an
  authoritative state transition as failed in a way that invites replay.
- Secrets, tokens, cookies, verification codes, raw provider payloads, private
  identifiers, Student IDs, full emails, contacts, and protected names do not
  enter Git, public UI, ordinary logs, or durable status documents.

## 5. Account-application state machine

Canonical states:

```text
EMAIL_UNVERIFIED
DRAFT
PENDING_ADMIN_REVIEW
CHANGES_REQUESTED
PENDING_DIRECTOR_APPROVAL
APPROVED_ACTIVATION_REQUIRED
ACTIVE
REJECTED
WITHDRAWN
EXPIRED
ARCHIVED
```

Minimum transitions:

```text
EMAIL_UNVERIFIED -> DRAFT
DRAFT -> PENDING_ADMIN_REVIEW
PENDING_ADMIN_REVIEW -> CHANGES_REQUESTED
CHANGES_REQUESTED -> PENDING_ADMIN_REVIEW
PENDING_ADMIN_REVIEW -> PENDING_DIRECTOR_APPROVAL
PENDING_ADMIN_REVIEW -> REJECTED
PENDING_DIRECTOR_APPROVAL -> CHANGES_REQUESTED
PENDING_DIRECTOR_APPROVAL -> APPROVED_ACTIVATION_REQUIRED
PENDING_DIRECTOR_APPROVAL -> REJECTED
APPROVED_ACTIVATION_REQUIRED -> ACTIVE
nonterminal applicant state -> WITHDRAWN
eligible expired state -> EXPIRED
retained terminal state -> ARCHIVED
```

Every transition requires an authenticated actor or verified private applicant
identity, authorization, an expected revision, an idempotency key where the
accepted write pattern requires one, a consequential-action reason where
applicable, a timestamp, durable transition history, and an audit/correlation
reference. Illegal, stale, replayed, or unauthorized transitions fail closed.

Administrator review validates the verified email, protected-directory result,
duplicate scan, affiliation, requested username, proposed account/access type,
role, committee, workspaces, operational scopes, Lending access, and effective
access preview. The Administrator cannot activate, self-approve the same
identity, grant System Owner, bypass sensitive capability policy, or supply the
Director approval.

Director review must use a different reviewer account and may approve, request
changes, or reject. It cannot grant System Owner or alter protected server-only
capabilities outside policy. Approval creates or updates the canonical account
atomically and enters activation-required state.

System Owner override is an exceptional break-glass path only. It requires an
authenticated owner, explicit reason, current-state confirmation, distinct
audit action, effective-access and session-impact capture, and a follow-up
review item. It is never presented as the normal path.

## 6. Identity, authentication, and verification

- Sign-in accepts normalized username, immutable operational account code, or
  a uniquely verified approved email, plus password.
- Errors remain generic; locked, disabled, archived, unverified, pending, or
  rejected identities do not gain a session.
- Sessions use the existing secure cookie, CSRF, expiry, rotation, revocation,
  and credential-version patterns.
- Password visibility controls are accessible and do not submit forms.
- Approved-email verification uses the existing approved provider and an
  owner-configured identity-class/domain registry. If no accepted values exist,
  the release stops before provider activation rather than hardcoding a domain.
- Verification challenges are single-use, hashed/protected at rest, rate
  limited, expiring, attempt limited, resend limited, and consumed atomically.
  Suggested defaults when no accepted existing policy conflicts are: 10-minute
  expiry, five attempts, 60-second resend minimum, and five sends per address
  per hour.
- The submission compares protected identity fields against the D1 roster
  projection; it does not query Google for every public request.
- Duplicate active account, pending application, archived account, protected
  roster, and identity-fingerprint checks return generic public responses.

## 7. Canonical access model

Reuse the existing account, role, capability, workspace, committee, location,
event, account-access-profile, session-revocation, audit, and protected roster
models. Extend them additively rather than creating another authorization
engine.

Effective access is computed on the server from account status, role/preset,
workspace assignments, default workspace, committee/location/event scopes,
capability grants and denies, self-service/internal-Lending flags, sensitive
capability policy, and explicit protected-account rules. Explicit deny and
protected-account rules win. Direct routes and API handlers enforce the same
result.

Minimum authorization matrix:

| Actor | Applicant self/status | Admin review | Director decision | Owner override | Accounts & Access | Internal workspace | Lending self-service |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Unauthenticated | Start/confirm/apply through private token only | Deny | Deny | Deny | Deny | Deny | Public paths only |
| Verified applicant | Own application/status/withdraw only | Deny | Deny | Deny | Deny | Deny | Per public policy |
| Staff without management capability | Own profile only | Deny | Deny | Deny | Deny | Assigned only | Explicit flag only |
| Administrator | Own profile | Authorized queue/actions except activation | Deny unless separately Director and not prior reviewer | Deny | Authorized by capability | Assigned only | Explicit flag only |
| Director | Own profile | Only if separately authorized | Authorized queue/actions; different reviewer required | Deny | Bounded management view per capability | Assigned only | Explicit flag only |
| System Owner | Own profile | Authorized | Authorized, still policy checked | Break glass with reason/audit | Full governed control except protected invariants | Assigned/governed | Explicit flag only |

Accounts & Access must support search, filters, sorting, pagination, safe detail,
current/proposed effective access, warnings, session impact, and accepted
retry-safe changes. It must preserve the last-active-Administrator, self-change,
system-account, and protected-owner controls.

## 8. My Profile

The profile displays the current avatar or initials, legal/display name,
verified email, username, contact, affiliation, role, committee, account code,
and summarized access as authorized.

- Legal identity, verified email, role, committee, capabilities, and account
  code are read-only on the self-service screen.
- Contact changes use server validation and audit/history.
- Username changes require current-password confirmation, uniqueness,
  normalization, protected history, session policy, and authoritative response.
- Password changes require current password, accepted password policy, safe
  session revocation, and audit without credential material.
- Identity corrections create a review request; they never silently mutate the
  protected D1 identity or Google source.
- Avatar is P1 and only uses the current private governed R2 media path. If that
  path cannot be accepted safely, initials remain the truthful fallback.

## 9. Operational domain requirements

### 9.1 Request Center

The first consequential choice is plain-language purpose:

- Event or Activity Support; or
- Office Inventory or Pantry Supply.

Each branch shows only relevant fields and explanations, shares server-side
identity/validation and private tracking, creates status/history/audit records,
and performs no stock deduction on submission. Unsupported or unavailable
branches explain the state and do not expose dead controls.

### 9.2 Integer quantities

Use one shared server validator for operational whole-number fields, including
request/lending quantities, inventory adjustments where authorized, counts,
initial quantities, low-stock thresholds, default loan days, announcement
order, and user-editable ranks.

- Parse the submitted value strictly as a base-10 integer string/number within
  the field's documented minimum and maximum.
- Reject fractions, scientific notation, `NaN`, infinity, ambiguous coercion,
  and out-of-range values. Direct API input `2.02`, `2.03`, and `0.06` must be
  rejected; `1` is accepted; `0` is accepted only where the field contract
  explicitly allows it.
- Client controls use appropriate number input metadata and plain validation,
  but the server remains authoritative.
- Existing fractional configuration is migrated only through an explicit,
  reviewed deterministic proposal; it is never silently rounded.

### 9.3 Low-stock alert

The control is explicit and plain-language:

```text
[ ] Enable low-stock alert
Low-stock alert at: [whole number]
```

It defaults off when no meaningful accepted threshold exists, accepts whole
numbers only, applies only to relevant stocked items, hides when irrelevant,
and creates attention/warning behavior only. It does not reserve stock, block a
valid transaction, or overwrite the inventory balance.

### 9.4 Core operational flows

- Public Request and Lending maintain private tracking and no submission-time
  reservation or stock movement.
- Internal Request review supports the accepted status, decision, history, and
  authorization model.
- Internal Lending supports identity verification, approve/partial/substitute/
  reject, ready-to-claim, handoff/issue, return, and accepted inventory/ledger
  invariants.
- Release Desk uses the canonical recipient-confirmed handoff and evidence
  model.
- Inventory retains canonical on-hand/reserved/available projections,
  classification fail-closed behavior, integer metadata, and ledger-only
  movement.
- Food and Materials minimum workspaces keep their accepted scoped workflows.

### 9.5 Link Registry and USC Announcements

Reuse the current canonical D1/server/service-adapter sources; do not create a
second link or announcement store.

- Critical Link Registry actions must be real, server authorized, audited, and
  show truthful synchronization/provider state. Provider failure must not
  corrupt or falsely complete the canonical mutation.
- Core Announcement draft, save, upload/preview, publish, schedule, pause, and
  archive controls must work or state why unavailable. Future and expired
  announcements are hidden from public presentation as defined by policy;
  failures do not block the portal; order is integer only.

## 10. Data and migration contract

Mapping must confirm the exact current schema and highest migration before a
number is assigned. v0.7.2 migrations are additive, forward-only, repeatably
testable, and compatible with the accepted backup/restore process.

Expected additive storage, subject to code-map confirmation:

- email-verification challenge and attempt/consumption metadata;
- account application, applicant-private status token/reference, revision, and
  retained transition history;
- Administrator and Director decisions and distinct reviewer identities;
- owner override/follow-up review evidence;
- normalized username uniqueness and protected username history;
- active verified-email fingerprint uniqueness;
- application code and write-idempotency uniqueness;
- identity-correction review requests;
- optional P1 notification/avatar references using existing provider patterns.

The migration must not rewrite immutable audit, ledger, evidence, request,
lending, account, roster, or identity history. Destructive table replacement,
data deletion, or lossy rounding requires a separately accepted amendment and
is out of scope.

Before any remote migration: verify exact target/bindings and schema, capture a
fresh private D1 export and recovery bookmark, retain the previous Worker
version, dry-run where supported, and prove isolated restore/replay. Afterward:
verify migration identity, integrity, foreign keys, row-count/invariant
reconciliation, health/readiness/version, and rollback/restore.

## 12. UX and accessibility acceptance

Use a bounded Hallmark audit/polish on critical v0.7.2 screens. Preserve the
existing HAU-USC identity, accepted visual tokens, architecture, routes, and
content intent. Do not apply a wholesale design-system rewrite.

Critical screens must provide clear hierarchy, one primary action per decision
state, labeled controls, inline field errors, safe summaries, truthful loading/
empty/error/unavailable states, and restrained visual treatment. Avoid dead
controls, fake metrics, excessive cards/pills, decorative gradients, or a
generic dashboard redesign.

Acceptance widths are 390, 820, and 1366 CSS pixels plus 200% zoom. Required
checks include keyboard-only operation, logical focus and restoration, visible
focus, accessible names/descriptions, error association and announcement,
contrast, touch targets, password toggle behavior, dialog safety, reduced
motion, no unintended document overflow, and readable long content.

  protected-data tests without sending real email in unit tests.
- Atomic account activation and account/access integration tests.
- Profile username/password/contact/correction/session tests.
- Request branch, integer validator, low-stock, public/internal operational,
  Link Registry, and Announcement tests.
- Migration fresh-apply, upgrade, constraint, recovery, and reconciliation

- Responsive/accessibility browser proof at all required sizes.

### 13.2 Repository and review gates

- Focused unit/integration suites pass after each bounded slice.
- Generated artifacts are rebuilt only through their source pipeline and pass
  deterministic parity.
- Repository-required format/lint/type/check/build/browser/Worker gates pass.
- Fresh independent R1 review passes the integrated identity/account/access

### 13.3 Isolated pre-production

distinct-reviewer and owner-override controls; profile/security; Request
branches and integer API denial; public/internal Lending; Release Desk; return;
Inventory/low-stock; role routes; Links; Announcements; responsive/accessibility;
redaction; concurrency/idempotency; cleanup; and rollback/restore.

Synthetic data and accounts are reconciled through accepted lifecycle controls;
immutable audit/history evidence is retained. Production is untouched.

## 14. Release, production, and rollback gates

After all repository, R2, and pre-production gates pass, freeze one exact
candidate SHA and prepare a GO package containing exact repository/PR/CI,
artifact, schema/migration, pre-production, backup/recovery, rollback,
configuration, smoke, canary, reconciliation, monitoring, and stop-trigger
evidence.

Production deployment is prohibited until the owner is shown the exact
candidate SHA and replies exactly:

```text
AUTHORIZE V0.7.2 PRODUCTION
```

Earlier execution authority does not satisfy that gate. After exact approval,
the sequence is backup/recovery refresh, target re-verification, migration,
Worker/static deployment, cache-busted identity/health checks, canaries,
incremental rollout, critical workflow smoke, invariant reconciliation,
synthetic cleanup/disablement, monitoring, and durable handoff. Any critical
trigger rolls back to the verified prior Worker/static version and accepted D1
recovery path before further action.

Critical rollback triggers include target or identity mismatch, staging binding
in production, broad login/registration failure, wrong identity authorization,
enumeration, pending/rejected access, same-reviewer approval, unintended access,
protected-data leakage, duplicate consequential writes, migration/integrity
failure, inventory/ledger failure, health/readiness/version mismatch, or an
unverified rollback.

Staging is rebaselined to the accepted production release only after production
acceptance and reconciliation; it is not silently mutated during candidate
development.

## 15. Work organization and ownership

The parent agent is the integration owner and sole writer to the release branch.
The owner-approved prompt allows a demand-driven ceiling of 16 active children,
but the current collaboration environment supports four active agents total;
therefore the practical ceiling is three child tasks plus the parent. Children
must not spawn grandchildren. Parallel tasks require non-overlapping ownership,
an exact base SHA, a bounded deliverable, verification, and stop conditions.

Read-only mapping/review children may run in parallel. Writer children, if used,
must use isolated worktrees and distinct files. The parent integrates one
verified result at a time, records status in the live registry, runs affected
tests, and rejects stale or contract-conflicting output. A child completion is
not acceptance until parent review and integration proof pass.

## 16. Stop conditions

Stop the affected path and report truthfully on any of the following:

- predecessor, branch, upstream, worktree, target, schema, binding, or release
  identity uncertainty;
- unknown overlapping work or endangered user files;
- an unaccepted migration/destructive-change need or immutable-history rewrite;
- missing backup, recovery point, rollback target, or isolated proof;
- unapproved email identity classes/provider or unavailable roster policy;
- authorization, privacy, sensitive-capability, protected-account, or
  applicant-enumeration uncertainty;
- an external MFA/CAPTCHA/account-selection/owner-only action;
- a private value at risk of entering Git, logs, evidence, or public UI;
- unresolved P0/P1 or mandatory `UNRUN` at pre-production/freeze;
- any production target mismatch or absence of the exact production phrase.

## 17. Definition of done

v0.7.2 is complete only when every P0 requirement is implemented or truthfully
accepted as unavailable where the prompt explicitly permits that state; all
state, API, access, data, UI, operational, security, privacy, accessibility,
migration, recovery, and rollback acceptance criteria pass; the exact candidate
has green repository/CI and R2 evidence; isolated pre-production is reconciled;
the owner separately authorizes the exact candidate; production is deployed,
canaried, reconciled, monitored, and handed off; staging is rebaselined; and the
repository records exact resulting SHAs and external-state boundaries.
