# HAU-USC Logistics v0.7.2 RV-01 Amendment

## Public Request Visibility, Review Ownership, and Deterministic Line Routing

This is the durable, owner-approved amendment to
`.codex/specs/v0.7.2-production-access-operations.md`. It is an additive
clarification and release re-gate.

It restores already-required behavior: working public requests, authoritative
internal review, capability-bound authorization, atomic transactions,
idempotency, target identity, and release acceptance. It does **not** authorize
a new product domain, a new authorization engine, a new queue family, or a
broad redesign.

All existing authorization, privacy, append-only history, audit, ledger,
reservation, retention, staging isolation, truthful-evidence, backup, rollback,
and production gates remain in force.

## RV-01.1 Canonical submission and durability

A public Request Center success response is returned only after the intended
Worker and D1 binding have committed or confirmed one canonical operation that
atomically creates or confirms: one parent request; one line per accepted
submitted line; one protected public tracking/access record; submission status
history; one public-submission audit event; idempotency/client-request
correlation; and global plus every immediately affected module/scope revision.

Parent and lines begin in the accepted review state, normally `FOR_REVIEW`.

Submission must not deduct physical stock, create a release, mark procurement
complete, create a receipt, or create a downstream operational owner.

Same key + same normalized payload returns the same canonical result with no
duplicate effect. Same key + different normalized payload fails safely through
the existing fingerprint binding. **RV-01 introduces no migration.** If payload
binding were to require one, all migration-free repairs are preserved and
promotion stops pending a separate additive amendment.

## RV-01.2 Authoritative internal Request module

The authenticated Request module independently returns the canonical parent and
line collections required by the review queue, with its own revision, total,
pagination, ordering, and filter metadata.

The D1 query and mapper, Worker endpoint, bootstrap/module allowlist, strict
validator, service contract, HTTP/REST adapter, module state replacement,
selector, and renderer must agree on one accepted contract.

The Request module must not depend on Overview loading first, on local storage,
on preview state, on a prior route, or on a full application bootstrap after
every submission.

Public/request-only contracts remain purpose-limited and never receive internal
queue data.

## RV-01.3 Capability-bound ownership of unassigned review work

Every unassigned `FOR_REVIEW` request is visible to at least one explicitly
authorized central review owner, through the existing capability and
effective-scope model. No role-name bypass is permitted.

| Context | Read unassigned review work | Review command |
|---|---:|---:|
| System Owner with verified central capability | Yes | Yes |
| Administrator with verified central capability | Yes | Yes |
| Director with verified central capability | Yes | Yes |
| Other central DOL reviewer defined by current grants | Per capability | Per capability |
| Relevant assigned committee | Within accepted scope | Within accepted scope |
| Unrelated committee/event/location | No | No |
| Requester-only | No | No |
| Lending-only | No | No |
| Explicit deny, disabled, archived | No | No |

A committee must not be auto-assigned merely to make a request visible.

## RV-01.4 Revisions and already-open REST sessions

Public submission updates the global, Overview, Request, and applicable visible
scope revisions. It must not increment Release, Deliverables/Procurement, or
Restocking when no object in those modules changed. After review/routing, only
every module/scope that actually changed is incremented.

The REST-backed Main Hub uses the existing revision mechanism, or the smallest
compatible extension, to check changed revisions while the authenticated
operational session is active; check immediately on route return, window focus,
reconnect, and explicit refresh; pause and back off while hidden or offline;
invalidate and refetch only affected modules; prevent duplicate concurrent
loads; prevent an older response overwriting newer state; keep errors safe and
recoverable; and avoid requiring a hard refresh, logout, or re-login for
ordinary queue freshness.

WebSockets, Durable Objects, a second cache authority, and a new event
architecture are out of scope for this repair. The interval and configuration
are centralized; polling constants are not scattered across views.

## RV-01.5 Pagination, filters, and stable order

The Request module computes its own total, page/page-size or cursor metadata,
`hasMore`, stable ordering with a deterministic tie-breaker, and
active/archive/date/search/scope filtering. It must not reuse Inventory's or
another module's count.

A newly submitted request within the active filter and scope must not disappear
because of stale search state, archive defaults, date boundaries, or another
module's page metadata.

## RV-01.6 Explicit per-line review and exactly one active route owner

The review command accepts one explicit permitted decision for each line, using
the repository's existing canonical enum and status names. Conceptual outcomes
are: issue from stock / reservation; procurement / canvass; catalog restock;
reject; missing information / return to review; and cancel only when already
accepted.

The server revalidates every decision against request purpose/type; line
identity and current status; item/catalog identity, archive state, and
classification; whole-number quantity and unit rules; authoritative availability
for stock routes; actor capability and effective scope; assignment, committee,
event, and location constraints; legal state transition; current route
ownership; and expected revision and idempotency.

Each non-rejected line has at most one active operational owner:

- stock/reservation — later Release eligibility only after accepted readiness
  rules;
- procurement/canvass — exactly one Deliverables/procurement item, and no
  Release before receiving/readiness;
- catalog restock — exactly one Restocking item, and no Event Deliverables
  duplication;
- missing information/rejected/cancelled — governed Request history state with
  no active downstream owner.

**The implicit default that routes every non-preclassified line to procurement
is removed.** An explicit accepted line decision is required.

A mixed request splits by distinct line identity while preserving one parent and
full traceability. The same line never appears in incompatible active queues.

Review and routing are atomic with status, assignment, route/reservation,
history, audit, idempotency, parent derivation, and affected revisions. Review
alone never creates physical stock movement; reservations change availability,
not on-hand quantity.

## RV-01.7 Expected downstream gating

These are required correct behavior, not defects: fresh `FOR_REVIEW` lines are
absent from Release Desk and Event Deliverables; fresh Office Inventory/Pantry
lines are absent from Restocking until accepted routing creates the work item;
submission does not deduct stock; stock routes reach Release only after review,
reservation/availability, and readiness; procurement routes reach Deliverables
only after explicit accepted routing; and Office Inventory/Pantry uses stock,
restock, or accepted split routing rather than a forced Event Deliverables
route.

## RV-01.8 Privacy and target identity

Public responses remain limited to the accepted receipt, safe status, and
private tracking contract. Internal stock, suppliers, internal notes, audit
internals, scope internals, tracking digests, raw tokens, and protected PII are
never exposed.

Before promotion, the public Request Center and authenticated Main Hub must be
proven to use the same intended release/source SHA, Worker build, static
artifact identity, environment, backend mode, schema and migration list, host
routing, and D1 target/binding, using an existing protected diagnostic or a
non-secret stable hash or safe label. A raw D1 database ID is never exposed
through a public endpoint, log, screenshot, report, or Git.
