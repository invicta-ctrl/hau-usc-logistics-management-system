## 1. Objective

Integrate the accepted V4.1 visual language — *Institutional Command /
Operational Choreography*, developed on `design/impeccable-whole-site-preview` —
into the authoritative HAU-USC Logistics front end, while preserving every
production route, workflow, form, action, status, permission boundary, and
service contract exactly as they behave today.

This is a presentation change. It is not a behaviour change.

## 2. Authority model

Applied in this order, per the owner brief:

1. **Production functionality is authoritative.** The deployed runtime defines
   what exists and what must not regress.
2. **Repository source matching production is the implementation authority.**
3. **The V4.1 baseline is the visual authority** for identity, typography,
   colour, shell composition, controls, motion, depth, and responsive
   behaviour.
4. **Accepted specifications remain the safety and invariant authority** —
   authorization, privacy, inventory/ledger invariants, request/lending/release
   semantics, audit and history behaviour, session boundaries, fail-closed
   behaviour, and staging/production separation.

**Conflict rule.** Where the visual baseline conflicts with real production
functionality, production functionality wins and the visual design adapts
around it. No working capability may be removed or weakened to make a screen
look better.

## 4. Scope

**Owner decision, 2026-08-09:** the whole front end is treated as a single
v0.7.3 slice.

This was proposed against a recommendation to split it into four slices
(public entry → shell/Overview → operational queues → inventory/administration).
The owner reaffirmed the single-slice scope. The trade-off is recorded in
§10 *Accepted risks* rather than silently absorbed.

### In scope

Front-end source and generated front-end artifacts only:

- Authoritative front-end source under `src/` — visual surfaces, components,
  styles, view templates, and front-end-only presentation logic.
- Generated front-end artifacts produced **through repository build scripts**
  (`dist/index.html`, the shareable application HTML, generated Apps Script
  HTML). These are rebuilt, never hand-edited.
- User-facing copy on front-end surfaces.
- Front-end animation and a progressive-enhancement 3D landing experience.
- Front-end, browser, accessibility, and visual-regression tests.
- The design and verification documents listed in §9.

### Out of scope

Back-end business rules, D1 schema or data, R2 behaviour, migrations, Worker
service contracts, Google Sheets/Drive writes, provider changes, the
auth/security model, deployment, staging or production mutation, DNS or domain
changes, release tagging, and merge.

If a visual requirement appears to need back-end work, current behaviour is
preserved and only the front-end treatment achievable with the existing
contract is implemented. The gap is recorded, not worked around.

## 5. Production surfaces that must be preserved

Derived from source at the integration base, not from the design preview's mock
registry.

**Workspaces** (`src/visual/workspace-routes.js`): `/admin`, `/director`,
`/food`, `/inventory`, `/materials`; canonical form `/{slug}/{module}`, with
`/app/{slug}/{module}` accepted as legacy.

**Modules** (`src/app/bootstrap-contract.js`): `overview`, `request`, `lending`,
`release`, `restocking`, `procurement`, `inventory`.

**View templates** (`src/visual/views/`): overview, request, lending, inventory,
release, restocking, procurement, reference-admin.

**Roles** (`src/domain/constants.js`): `SYSTEM_OWNER`, `ADMINISTRATOR`,
`DIRECTOR`, `COMMITTEE_HEAD`, `DOL_STAFF`, `REQUESTER`, `READ_ONLY_AUDITOR`.

**Public and pre-authentication surfaces** (`src/visual/`): `auth-gateway`,
`public-requester-portal`, `public-lending-portal`, `public-account-application`,
`requester-portal`, `borrower-lending-portal`, `public-policy`, `brand-assets`,
`public-advertisement-carousel`, `portal-navigation`.

**Authenticated shell**: `runtime`, `runtime-extensions`,
`authenticated-account-controls`, `bootstrap-controller`, `bootstrap-ui`,
`form-dirty-state`.

**`reports` has no bootstrap module and no view template.** It must not be
given a user-facing surface by this work.

## 6. Copy standard

Domain language is kept. Implementation language is removed from ordinary
user-facing screens.

**Keep:** Request, Lending, Release, Inventory, Restocking, Receiving,
Canvassing, Procurement, Event, Sub-event, For Review, Ready to Release, Ready
to Claim, Overdue, Returned.

**Remove from ordinary UI:** backend, runtime, bootstrap, API, provider, D1, R2,
Cloudflare, schema, migration, canonical, reconciliation, binding, environment
identity, payload, revision token, idempotency, server-authoritative,
projection, DTO, adapter, Worker.

Headings 2–6 words. Descriptions usually one sentence, 8–18 words. Buttons are
direct verbs. Every error answers: what happened, what was saved, what to do
next. No environment badge in production; staging shows "Test site" in plain
language, never an infrastructure name.

All enum values continue to pass through
`src/domain/presentation-labels.js`. No raw enum reaches the interface.

## 7. Preview chrome that must not ship

The visual baseline was developed inside a preview harness. None of it ships:
surface picker, state picker, role-debug picker, viewport simulator, mock-data
labels, fictional actor selectors, preview environment bar, version-comparison
controls, "v4.1" or "Kinetic Institutional Operations" labels, design-test
instrumentation, and illustrative-data disclaimers that existed only because the
baseline was a preview.

The baseline supplies design. It does not supply chrome.

## 8. Invariants that must remain visible in the interface

- Request submission does not deduct stock.
- Acceptance and reservation are distinct from physical release.
- Release can be partial and cumulative.
- Lending review, ready-to-claim, handoff, on-loan, overdue, and return are
  distinct states.
- Inventory movement history is append-only; direct balance editing is never
  presented.
- Controls never imply capability the actor lacks; hiding a control is not
  authorization.
- Public views expose no protected stock, internal notes, roster data,
  supplier or private evidence, or audit internals.
- Failure states state what saved, what did not, and the next safe action.

## 10. Accepted risks

1. **Single-slice scope.** Rollback granularity is one commit range for the
   entire front end rather than four independently revertible slices, and
   functional parity must be proven across ~30 surfaces at once before any part
   can land. Mitigation: the parity baseline in §9 is captured *before* the
   first source edit, and parity is proven per journey with browser evidence.
2. **3D landing experience.** Adds a front-end dependency and a performance
   surface. Mitigation: progressive enhancement only, static fallback, lazy
   start after critical content, pause when hidden or off-screen, reduced-motion
   and save-data respected, no critical action dependent on WebGL, measured
   bundle delta recorded.
3. **Generated artifacts.** `dist/index.html` and the shareable HTML are
   regenerated, so the diff is large and mostly mechanical. Mitigation: never
   hand-edited; regenerated through repository scripts and verified.

## 11. Verification

Before handoff:

- Relevant unit and component tests.
- Browser tests across the production journeys in §12.
- Accessibility: landmarks, headings, visible focus, keyboard operation,
  modal/drawer focus containment and restoration, state announcements, no
  colour-only meaning, contrast, 200% zoom, touch targets, reduced motion,
  safe behaviour at 320 px.
- Responsive at 320, 375, 414, 768, 1024, 1440.
- `npm run check` where repository governance requires it.
- Generated-artifact verification.
- `git diff --check`.
- Measured front-end bundle and runtime delta, recorded.

Assertions are not weakened to fit the new design.

## 12. Functional parity gate

No acceptance without browser evidence for each journey: public Request
submission and tracking; public Lending submission and tracking; staff sign-in;
role landing; Request review; Lending review; Release; Return; Inventory;
Restocking and Receiving; Accounts and Access where authorized; Link and
Announcement actions already in production.

Each records: fields preserved, actions preserved, service contract unchanged,
authorization unchanged, status semantics unchanged, mobile verified.

## 13. Rollback

Git and source based. Before the first production front-end edit, record the
exact starting SHA and the rollback commit, and capture production front-end
screenshots. No duplicate production files are created inside the application
tree. Production is never a rollback target for this work because this work is
never deployed under this specification.

## 14. Stop conditions

Stop and report rather than improvise if: a change would require back-end,
service-contract, migration, provider, or environment work; the release branch
or a protected artifact would be written; real private data would be needed;
a production route cannot be verified from authoritative source and would have
to be invented; functional parity cannot be proven; accessibility or performance
cannot be brought to standard without reducing the visual effect — in which case
reduce the effect, never the gate; or the writer lock cannot be claimed cleanly.

## 15. Release boundary

This specification authorizes front-end implementation on the accepted working
branch **after** it is accepted and the writer lock is claimed. It does not
authorize deployment, staging, merge, release tagging, provider writes, or
migration application. The task ends at a verified implementation candidate.

## 17. Implementation order

The whole front end is one accepted slice, but it is built and verified in a
fixed order so that a failure is diagnosable and the parity gate is provable:

1. **Rollback evidence** — record the starting SHA and capture production
   front-end screenshots *before* the first source edit (§13).
2. **Design foundation** — tokens, type, depth, motion, icon treatment.
3. **Shell and signature controls** — rail, topbar, celestial toggle, kinetic
   menu, compact back control, mobile navigation.
4. **Public entry and landing**, including the progressive-enhancement 3D hero
   and its static fallback.
5. **Operational surfaces** — Overview, Request, Lending, Release, Restocking,
   Procurement, Inventory.
6. **Administration surfaces.**
7. **Copy pass** across every surface against §6.
8. **Preview-chrome sweep** against §7.
9. **Verification and the parity gate** (§11, §12).

Each step is committed separately on the working branch so the single-slice
scope still yields a reviewable, bisectable history.
