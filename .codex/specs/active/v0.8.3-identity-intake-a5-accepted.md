## A6 owner-accepted identity decision table

### 1. Stable person key

Every canonical person receives one immutable opaque internal `person_id`. It
is never derived from email, name, student number, phone, department, role, or
other mutable human data. Reuse the repository's canonical identifier
generator when present; otherwise use a cryptographically safe opaque ID.
External/source identifiers are provenance fields. Changing email, name, or an
assignment never changes `person_id`.

### 2. Email rules and cardinality

A person has zero or more emails, may exist without email, and has at most one
PRIMARY email at a time. Preserve display/original form; normalize lowercase
and trim only for matching. One verified active normalized email may belong to
at most one canonical person. Collisions do not auto-merge people and are
flagged/quarantined when ambiguous. Email changes do not change `person_id` or
silently break an explicit `account_staff_link`; historical/superseded emails
may remain as provenance. Never create placeholder emails.

### 3. Accounts per person

An account links to zero or one canonical person; a canonical person may link
to zero or more accounts. Each account independently satisfies the existing
authentication lifecycle. Never link by name similarity. A unique verified
email match is migration evidence only when unambiguous; once accepted, persist
an explicit `account_staff_link`. Do not retain runtime email joins as the
canonical link, and preserve existing valid access unless an explicit
security/owner rule revokes it.

### 4. Duplicate assignments

Do not merge people because assignments look similar. Assignment identity
considers `person_id`, organization/office/department, role, effective period
when known, and source/provenance ID when available. Collapse exact duplicates
only when they represent the same real assignment, retaining source-row
provenance. Different role, department, office, term, effective period, or
source meaning remains separate. Preserve and flag ambiguous duplicates.

### 5. Effective dating, source authority, and rollback

Never invent effective dates: preserve authoritative values, otherwise use
`NULL` for `effective_from` and `effective_to`. A current accepted roster may
prove CURRENT/ACTIVE status without a fabricated start date. Source precedence
is: current Earl accepted roster/instruction; current accepted repository/domain
records plus verified Production account state; current authoritative project
roster/source files; legacy Sheets/Drive mirrors and preserved migration
sources; then historical/superseded provenance only. Use expand-first changes,
back up before mutation, preserve source/provenance, avoid destructive drops
before parity proof, retain a bounded rollback projection and reconstruction
evidence.

### 6. Authorization projection

`person_id` is identity, `account_staff_link` is account-to-person binding,
assignments are organizational/role facts, and authorization is an explicit
role/capability projection. An account link alone grants no privilege.
Missing/ambiguous data grants none; explicit deny/revocation/restriction wins.
During migration preserve the existing valid effective-access baseline. New
assignment-derived privileges require an explicit accepted mapping; never infer
privilege from name, email, or department text. Retire compatibility access
only after an explicit verified transition.

## Accepted implementation envelope

- ID-A remains passed: token-digest, CSRF, credential-version, expiry,
  rate-limit, generic-error, and session-revocation contracts are preserved.
- Complete ID-B through ID-H one bounded, reviewable slice at a time:
  canonical person and assignment domain, email/provenance and explicit account
  linkage, existing active-access preservation, two-stage approval, Staff
  Directory, activity history, and secure eight-digit verification with resend
  invalidation/backoff and existing email delivery integration where required.
- Restore the reusable password show/hide control on every applicable current
  password-entry surface. It is hidden by default, preserves the exact value,
  is keyboard and screen-reader operable, does not submit forms, preserves
  autocomplete/password-manager behavior, and never logs or persists the
  password. Reuse existing component, icon, token, and architecture patterns.
- Browser verification precedes any Figma interaction for the password slice.
  No Figma/Make access occurs before that evidence is ready.

## No-fabrication and safety boundary

Never invent business identities, contacts, assignments, dates, approvals,
provider identifiers, credentials, URLs, external records, test results,
migration results, deployment results, or performance numbers. Search one
minimum authoritative in-scope source; derive mechanically where possible;
use a canonical generator only for internal technical identifiers; otherwise
preserve `NULL`, UNKNOWN, UNRESOLVED, or QUARANTINED as the schema permits.
Stop only for a true safety, privacy, credential, irreversible-data, crossover,
or unresolvable-authority blocker. Commit/push safe work and persist/release
the writer lock before any such stop.

## Explicitly excluded from the first bounded slice

- No fabricated roster/business truth, automatic person merge, implicit
  privilege grant, destructive migration, backfill/import, or provider action.
- No Figma/Make or route-design inspection until password browser evidence is
  ready and the A6 readiness path applies.
- No v0.8.2 reopening and no v0.9.x work.
