# HAU-USC Logistics v0.7.0 Hybrid Evidence Storage Amendment

This is the durable, owner-approved amendment to Phase 16 of
`.codex/specs/v0.7.0-production-master.md`. It supersedes any earlier requirement
that made Google Drive the synchronous or authoritative evidence store.
Cloudflare R2 is the operational source of truth. Google Drive is a private,
asynchronous secondary backup and owner-accessible recovery archive.

All existing authorization, privacy, audit, append-only history, retention,
staging acceptance, truthful-evidence, rollback, and production gates remain in
force.

## Primary write contract

For every website-uploaded photo or document:

1. Validate authorization, declared file type, file signature, and size.
2. Write the accepted bytes to the correct private R2 bucket under a governed,
   non-user-controlled object prefix.
3. Verify the R2 object after the write.
4. Atomically commit the R2 object key, checksum, size, MIME type, related
   record, retention metadata, audit metadata, and a Google Drive backup job to
   D1.
5. Complete the related Release Desk, Lending, Receiving, or Procurement
   workflow only after the R2 verification and D1 transaction pass.
6. Process the Google Drive backup asynchronously.

Google Drive availability must never be part of the synchronous operational
transaction. A failed R2 verification or D1 transaction fails the related
workflow. A temporary Google Drive failure does not roll back an already
accepted R2 and D1 result.

## Google Drive backup contract

- Read the accepted primary object from R2.
- Upload only to the approved private Google Drive backup folder.
- Use a stable idempotency key derived from the evidence ID and checksum.
- Verify the resulting Drive file ID, size, parent folder, and checksum where
  the provider supports the checksum.
- Keep the Drive file ID and provider diagnostics in protected D1 fields.
- Mark a backup `SYNCED` only after verification.
- Retry temporary failures with bounded backoff.
- Move exhausted or permanent failures to an owner-review state.
- Never create multiple Drive copies for one evidence version, including after
  duplicate queue delivery.
- Never create a public link or grant public access.
- Never enumerate, read, modify, or delete unrelated Google Drive content.

The permitted backup states are:

- `PENDING`
- `IN_PROGRESS`
- `SYNCED`
- `RETRYING`
- `FAILED`
- `RESTORE_REQUIRED`
- `ARCHIVED`

## User-facing messages

After the R2 and D1 transaction succeeds:

> ✓ Your photo or document is saved securely. A backup copy will be created
> automatically.

When the backup is delayed:

> ! The file was saved, but its backup is still pending. The system will try
> again automatically.

Ordinary UI and logs must not disclose bucket names, object keys, Drive file
IDs, OAuth values, or raw provider errors.

## Governed restore

The application must provide an Owner-only restore operation:

1. Read the selected private Google Drive backup.
2. Validate authorization, type, signature, size, and checksum.
3. Restore to the governed R2 object key only when the original object is
   missing or invalid; otherwise use a new versioned key.
4. Never silently overwrite a valid R2 object.
5. Verify the restored R2 object.
6. Update protected metadata atomically.
7. Append Activity History and audit records.

Unauthorized users must not inspect backup metadata, initiate a restore, or
retrieve provider identifiers.

## Retention, archival, and deletion

- R2 remains the operational source of truth.
- Drive remains the secondary recovery copy.
- Archive before deletion.
- Apply approved R2 lifecycle and bucket-lock policies.
- Archiving an operational record does not immediately delete its Drive backup.
- Permanent deletion requires explicit Owner authorization, recorded
  reconciliation, and satisfaction of legal, audit, operational, and rollback
  retention requirements.

## System Owner status

The protected System Status experience must expose:

- primary R2 status;
- pending Drive backups;
- failed backups;
- oldest pending backup;
- last successful backup;
- last reconciliation;
- files requiring restoration.

Provider identifiers and raw provider errors belong only in protected Technical
Details.

## Required acceptance evidence

Prove all of the following with focused automated coverage and staging evidence:

1. R2 succeeds while Drive is unavailable.
2. The related workflow still completes safely.
3. The backup job retries.
4. Duplicate job delivery creates no duplicate Drive file.
5. Drive backup verification passes before `SYNCED`.
6. An Owner can restore a backed-up file.
7. Unauthorized users cannot inspect or restore backups.
8. No public file link is created.
9. Secrets and private storage identifiers do not appear in logs or ordinary
   UI.

Production remains gated until the complete v0.7.0 master specification, all
accepted amendments, and every required final acceptance gate pass.
