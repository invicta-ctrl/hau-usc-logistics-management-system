## Integration rules

- The browser uses only the Worker/API. It never receives a D1 database identifier, R2 bucket name, provider identifier, object key, recovery reference, or private configuration.
- `D1` below identifies the server-owned domain tables used by the existing contract. `R2` identifies the existing authorized media/evidence service, never direct browser access.
- `SUPPORTED` means an existing V5 surface and current backend contract can be connected without changing the frozen visual contract.
- `PARTIAL` means real data can be shown, but one or more visible prototype controls cannot safely call an existing command with the information the surface collects.
- `PROTOTYPE_ONLY_UNSUPPORTED` remains non-destructive. It is not replaced with invented behavior.
- `BACKEND_CAPABILITY_NOT_EXPOSED_BY_V5` remains available server-side and is not imported visually.

## Control classification

### Real backend actions

- Sign in/sign out; public request options, new-request submit, and request tracking; public lending catalog and submit; valid in-memory safe tracking projections.
- Request queue refresh, scoped selection, review/routing/reservation when the existing V5 controls collect a complete valid command.
- All listed bootstrap/module/detail/directory/reference/brand/profile/health read refreshes where the current capability allows them.
- Hash navigation, theme, drawer, tabs, command palette, local draft-line editing, and presentation filtering remain client-only UI behavior.

### Prototype-only unsupported controls

- `public.register` direct **Create account**.
- `public.verify`, `public.application`, and `public.application-status`, because the complete verified-email/application receipt/status-token lifecycle is absent and provider/email sends are excluded from this task.
- `public.request-intake` additional-request mode, because the current V5 control does not prove private access to the parent request.
- `public.lending-intake` direct evidence-file selection, because the public contract does not authorize a direct R2 upload.
- `lending.detail` standalone **Add note**.
- `lending.detail` return, `release.desk` release/evidence, and `account.profile` password mutation because their complete governed command inputs are absent.
- `restocking.queue`, `procurement.board`, `events.series`, `admin.access`, `admin.reference`, `admin.links`, and `admin.brand` controls currently emitted as `data-act="noop"` because their complete governed command forms are absent.
- Any action button whose visible surface lacks mandatory revision, reason, identity/evidence, quantity, or target fields remains non-destructive; the adapter must not guess missing values.

## Backend capabilities intentionally not exposed by V5

The following existing capabilities remain intact and are classified `BACKEND_CAPABILITY_NOT_EXPOSED_BY_V5` unless an existing V5 control already supplies every required input:

- Account Access ID preview/change, policy preview/update, starter-account seeding, password reset, session revocation, unlock, owner override, and identity-roster apply/rollback.
- Composite-request reopen/amend/cancel, section addition, component assignment/escalation, and specialized food/materials/venue workflows.
- Full canvass create/update/archive/preferred workflow; restock transition/receipt detail; deliverable receipt; release correction.
- Inventory create/update/archive/restore, classification/bulk classification, storage-context change, cycle-count adjustment, reusable-asset reassignment/maintenance, and event-item transfer.
- Lending approval, handoff, reusable-asset registration/maintenance, usage export, and administrative lending reporting.
- Event series/day/activity mutation and operational-record linking.
- Advertisement create/edit/upload/publish/schedule/pause/resume/archive and governed brand-asset upload/publish/rollback where V5 provides only a summary row.
- Reference-link creation/version transition and full reference-administration review workflow.
- Owner evidence backup processing/restore/archive, migration diagnostics, playground reset/baseline refresh/tester/module-switcher controls, and all production release operations.

## Data provenance proof contract

Each connected route test must record: route, exact API contract, D1 domain, R2 domain, required capability, synthetic record/reference, and observed mapped result. A route is not connected merely because the frozen mock still renders. Mock arrays must be empty or replaced by API-derived view models for every supported internal route.
